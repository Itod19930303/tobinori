# Issue実装ワンコマンドスキル

このスキルは `docs/development-harness.md` に定義された開発フロー（TDD → レビュー → コミット）を、Issue番号を受け取って一気通貫で実行する進行役を担う。各工程の実作業は専用エージェント（`flutter-test-writer` / `flutter-feature-implementation` / `flutter-code-review` / `spec-compliance-review` / `flutter-ux-review`）に委譲し、このスキル自身は進行管理とレビュー通過ゲートの管理を行う。

詳細設計は対象外（`design-issue` スキルの担当）。**このスキルが呼び出された時点で、対象Issueの詳細設計はユーザーの承認が済んでいるものとして扱う。**

## 進行フロー

### 0. 事前確認
1. `git status` を確認し、未コミットの変更がないか確認する（あれば先に相談する。作業中の変更を巻き込んで進めない）。
2. `gh issue view <番号>` でIssue内容を取得する。
3. `docs/design/issue-<番号>-*.md` の詳細設計書が存在するか確認する。
   - **存在しない場合**: 実装を進めず、先に `design-issue` スキルで詳細設計を行うようユーザーに伝えて終了する（設計なしに独自解釈で実装を進めない）。
4. 対象ブランチ（`issue-<番号>-<内容を表す英語スラッグ>`）が無ければ `main` を最新化して作成する。既にあればチェックアウトする。

### 1. TDD実装フェーズ
1. `flutter-test-writer` を呼び出し、詳細設計書の「7. テスト観点」に基づいて失敗するテストを作成させる（Red）。
2. `flutter-feature-implementation` を呼び出し、詳細設計書のクラス設計に沿ってテストを通す実装をさせる（Green）。
3. 機能が複数の小さな単位に分けられる場合は、1〜2を単位ごとに繰り返してよい。
4. すべてのテストが通っている（Green）ことを確認してから次のレビューフェーズに進む。

### 2. レビューフェーズ
1. `flutter-code-review`、`spec-compliance-review` を呼び出す（対象に画面が含まれる場合は`flutter-ux-review`も呼び出す。スクリーンショットが必要な場合はユーザーに実機/エミュレータでの確認・共有を依頼する）。
2. 各レビュー結果を集約し、ユーザーに提示する。

**ゲート（レビュー通過）**: いずれかのレビューで「重大（修正必須）」に相当する指摘がある場合、**コミットは行わない**。`flutter-feature-implementation` を再度呼び出して該当箇所を修正し、修正後に該当エージェントで再レビューする。これを重大な指摘がゼロになるまで繰り返す。「推奨」レベルの指摘は、対応するかユーザーに確認したうえで進めてよい（保留してコミットに進むことも可）。

### 3. コミット・PRフェーズ（ゲート通過後）
1. 変更点を `git status` で確認し、コミットする。コミットメッセージ末尾に `#<Issue番号>` を含める。
2. `git push -u origin <ブランチ名>` する。
3. `gh pr create` でPRを作成する。本文に `Closes #<Issue番号>` を含め、実施したテスト・レビューの概要をSummaryとして記載する。
4. PR URLをユーザーに提示して完了を報告する。

## 心がけること

- 各フェーズの節目（テスト作成後、実装後、レビュー結果提示時、コミット前）で必ずユーザーに状況を報告する。サイレントに先の工程まで進めない。
- レビュー通過ゲートは必ず守る。重大な指摘が残ったままコミットしない。
- 「ワンコマンド」とはいえ全自動でユーザーの目を通さず進めるという意味ではない。各エージェントの実行そのものは自動で連続して行ってよいが、ゲートでは必ず立ち止まる。
- 出力・報告はすべて日本語で行う。
