# Issue詳細設計スキル

このスキルは、Issue単位の詳細設計書（`docs/design/issue-<番号>-*.md`）を作成し、要件定義書・アーキテクチャ設計書との抜け漏れを自動レビューしたうえで、ユーザーとの対話を通じて設計を確定させる進行役を担う。**ここで得られるユーザーの合意が、後続の`implement-issue`スキルにおける実装着手の前提（承認）となる。**

## 進行フロー

### 1. 事前確認・ブランチ作成
1. `gh issue view <番号>` でIssue内容を取得する。
2. `git status` を確認し、未コミットの変更を巻き込まないようにする。
3. 対象ブランチ（`issue-<番号>-<内容を表す英語スラッグ>`）が無ければ `main` を最新化して作成する。既にあればチェックアウトする。

### 2. 詳細設計書の作成
1. `flutter-detailed-design` エージェントを呼び出し、詳細設計書（`docs/design/issue-<番号>-*.md`）を作成させる。

### 3. 自動レビュー（設計書の抜け漏れチェック）
1. `detailed-design-review` エージェントを呼び出し、作成した設計書を要件定義書・アーキテクチャ設計書と突き合わせてレビューさせる。
2. 「抜け漏れ・要修正」に該当する指摘がある場合は、`flutter-detailed-design` を再度呼び出して設計書を修正し、指摘がなくなるまで 3.1〜3.2 を繰り返す（ユーザーに都度確認を挟まず、自動レビューが通るまでは内部でループしてよい）。

### 4. ユーザーとの対話による確定
1. 自動レビューを通過した設計書の要約と、「8. 未決定事項・確認したい点」をユーザーに提示する。
2. ユーザーからのフィードバック（修正指示、未決定事項への回答、懸念点の指摘など）があれば、`flutter-detailed-design` を呼び出して設計書に反映し、必要なら再度 `detailed-design-review` にかける。このやり取りは何度でも繰り返してよい。
3. ユーザーから明確な異論・追加の指摘がない状態になったら、「この設計で実装（`implement-issue` スキル）に進めます」と伝えて締めくくる。

## 心がけること

- 自動レビュー（ステップ3）は仕様の抜け漏れという客観的な観点のチェックであり、ここでの往復はユーザーの手を煩わせず内部で完結させる。
- ユーザーとの対話（ステップ4）こそが本質的な承認プロセスである。ここを省略したり、生成しただけで「完了」と報告したりしない。
- 出力・対話はすべて日本語で行う。
