# アーキテクチャ設計・技術選定 - トビノリ

> 本ドキュメントは `docs/requirements.md`（2026-09-15更新版、Flutter採用・Google Maps Platform確定版）を入力として作成した。開発体制は「個人開発・プログラミング未経験に近い・実装はClaude Codeを活用」という前提に基づき、**学習コストの低さ**と**Claude Codeでの生成・保守のしやすさ**を最優先の判断基準とする。要件定義書の未確定事項についても、断定が難しいものは選択肢＋推奨案の形で方針を示す。
>
> **2026-09-15 改訂の主な変更点**: モバイル実装方式を「Kotlin + Jetpack Compose（Androidネイティブ）」から **Flutter（Dart）によるAndroid/iOSクロスプラットフォーム開発** に変更。乗換案内APIは **Google Maps Platform に確定**。オフライン時は**明示的な状態表示方式**に確定。最寄り駅までの経路案内は**Googleマップアプリへのインテント連携**に確定。プライバシーポリシーは簡易なものを用意する方針で確定。これに伴い、状態管理・ローカルDB・認証SDK・CI/CD・秘密情報管理をFlutterエコシステム向けに全面的に見直した。
>
> **追加改訂（同日）**: (1) Apple Developer Program（年会費$99）がiOS対応時に事実上必須である点は確定情報としつつ、費用負担への同意自体はiOS対応着手時までの保留事項として整理。(2) Google Maps Platformの予算アラートを、課金額$1到達時点で通知が来るよう設定する方針を確定。
>
> **再改訂**: 認証機能（Firebase Authentication経由のOAuthログイン）をMVPスコープから全面的に除外することを確定。検索履歴がローカル保存のみでユーザーごとの出し分けが不要なこと、「調べる→確認するを最速に」というコンセプト上ログイン画面を挟むことが好ましくないことが理由。これに伴い、Firebase Authentication・Identity Platform（LINE OIDC統合）・各社OAuthプラグインの導入は不要となり、バックエンドレス構成がより単純化された（認証なし・自前サーバーなしの完全クライアント完結構成）。将来、複数端末間の履歴同期等のニーズが生じた場合に認証基盤の導入を再検討する。

**構成上の最大の特徴（個人開発向けの割り切り）**:
- 自前のアプリサーバーは持たない「バックエンドレス構成」を基本とする。検索履歴もクラウド同期しないため、サーバーで状態を持つ必要がない。認証機能もMVPでは持たないため（5章参照）、外部サービスはGoogle Maps PlatformとGoogleマップアプリのみで完結する。
- モバイル実装は **Flutter（Dart）単一コードベース**とし、Android/iOSの両対応を1つの実装で実現する。まずはAndroid 15実機での動作確認を行い、iOS対応は将来（1年以内目安）に本格着手する。
- 経路検索APIはGoogle Maps Platform（Routes API）に確定。構造化JSONを取得し、トビノリ独自のデザインシステム（カードUI）でアプリ内に表示する。
- 秘密情報（Google Maps PlatformのAPIキー）はGoogle Cloud側の制限機能（アプリケーション制限・API制限）で保護し、クライアントに埋め込む秘密は「漏れても実害が小さい・制限をかけられるもの」に限定する（8章）。

## 2. モバイル実装方式

- **選定: Flutter（Dart）によるAndroid/iOSクロスプラットフォーム開発**
- **理由**:
  - ユーザー要件として「1年以内目安でiOS対応も行いたい」という明確な意向があり、単一コードベースで両OSに対応できるクロスプラットフォームフレームワークが必須の前提となった。
  - Flutterは学習資料・公式ドキュメント・サンプルコードが豊富で、Claude Codeの生成精度・知識量も高い（widget単位で完結する宣言的UIは、Claude Codeにとってもコード生成・差分修正がしやすい構造）。
  - `ThemeData`（マテリアルテーマ）でカスタムカラースキーム・フォント（`google_fonts`パッケージ経由でJetBrains Mono / Noto Sansを利用）・角丸8pxのグリッドをDESIGN.mdの定義通りにマッピングしやすい。
  - GPS・ローカルDB・秘密情報管理など、要件にあるネイティブ寄りの機能も、プラグイン経由（`geolocator`, `sqflite`, `flutter_secure_storage`等）でAndroid/iOS双方に対応できる。
  - Google Maps Platformは公式にFlutter向けの利用実績が豊富であり、両OS対応時も追加実装コストが小さい。
- **比較した代替案とトレードオフ**:
  | 選択肢 | メリット | デメリット |
  |---|---|---|
  | **Flutter（採用）** | 単一コードベースでAndroid/iOS両対応。UIが宣言的で学習・Claude Code生成ともに扱いやすい。Google製で長期サポートの見通しが立てやすい | Dartという新しい言語の習得が必要（ただしKotlin習得と比べて大きな差はない） |
  | React Native | JS/TSの知識があれば流用しやすい | 開発体制に既存スキルなし。ネイティブモジュール導入や環境構築（Node/Metro等）がFlutterと比べて複雑になりやすい |
  | Kotlin + Jetpack Compose（旧方針） | Android単体なら学習対象が絞られる。公式・情報量が最大 | Android専用。iOS対応時に実装を丸ごと作り直す必要があり、今回のユーザー意向（1年以内のiOS対応）と不整合 |
  | Kotlin Multiplatform (KMP) + Compose Multiplatform | ロジックはKotlinで共有しつつネイティブUIも書ける | Flutterと比べるとComposeMultiplatformのiOS対応はまだ発展途上で、学習資料・Claude Codeでの実績もFlutterに劣る |

  → iOS対応の意向が明確なため、**Flutterを推奨**。

### 2.1 開発ターゲット・動作確認方針
- 開発時の実機確認は開発者所有の **Android 15端末** で行う。
- `minSdkVersion` はAndroid 15専用に絞らず、Flutterの標準的な対応水準を踏まえ **Android 7.0（API 24）以降** を目安とし、幅広い端末で動作する汎用的な作りとする。
- iOS対応は将来（1年以内目安）に着手予定。Flutter採用によりUI・ロジックの大部分は流用できる見込みだが、以下はiOS対応時に追加検討が必要（9章に記載）。
  - Apple Developer Programへの登録（年会費$99。ストア配布しない場合でも実機への長期インストールには事実上登録が必須であることは確定情報。ただし**費用負担への同意自体はiOS対応着手時までに判断する保留事項**とする。9章参照）
  - iOS向けの署名・プロビジョニングプロファイルの設定

### 2.2 状態管理

- **選定: Riverpod（`flutter_riverpod` パッケージ、コード生成なしの素朴な `Provider`/`StateNotifierProvider` スタイルを基本とする）**
- **理由**:
  - 2026年時点のFlutterコミュニティでは、新規プロジェクトの状態管理として**Riverpodが実質的な標準**になっている。`BuildContext`に依存せず、テストや将来のロジック分離もしやすい。
  - Claude Codeでの生成実績・情報量もRiverpodが豊富であり、誤ったコードを生成しにくい。
  - 一方でRiverpodには「コード生成（`@riverpod`アノテーション + `build_runner`）」を使う流儀もあるが、`build_runner`の実行はプログラミング未経験者には追加のトラブルシューティング要因になりやすいため、**MVPでは手書き（コード生成なし）のRiverpod**を採用し、シンプルな`Provider` / `StateNotifierProvider` / `FutureProvider`の組み合わせに留める。将来アプリが複雑化した場合にコード生成スタイルへ移行する余地を残す。
- **比較した代替案とトレードオフ**:
  | 選択肢 | メリット | デメリット |
  |---|---|---|
  | **Riverpod（コード生成なし・採用）** | 2026年の実質デファクト。テスト容易・BuildContext非依存。Claude Codeでの生成実績多数 | Providerよりわずかに概念（`ProviderScope`等）を覚える必要がある |
  | Provider（`provider`パッケージ） | Flutter公式チュートリアルでも長く使われ、概念が単純（`InheritedWidget`の薄いラッパー） | 大規模化時にコンパイル時安全性で劣る。2026年時点では新規プロジェクトでの採用理由が薄れている |
  | Bloc/Cubit | 大規模チーム開発での型安全性・テスト容易性に定評 | 学習コスト（イベント/状態の設計パターン）が本プロジェクトの規模には過剰 |

  → 今回はMVP規模かつ将来の拡張性も考慮し、**Riverpod（コード生成なし）を推奨**。

### 2.3 ローカルDB

- **選定: `sqflite`（SQLite）**
- **理由**:
  - 保存対象は「検索履歴」という単一の小さなテーブルのみであり、生SQLを直接扱う`sqflite`で十分にシンプルに実装できる。
  - `drift`（旧moor）は型安全なクエリ生成やマイグレーション支援に優れるが、`build_runner`によるコード生成が前提となり、Riverpodのコード生成と合わせて未経験者にはビルドエラー対応の負荷が増える懸念がある。
  - Claude Codeは`sqflite`のCRUDコード生成に十分習熟しており、小規模スキーマであれば型安全性の恩恵よりもシンプルさを優先する方が運用しやすい。
- **比較した代替案とトレードオフ**:
  | 選択肢 | メリット | デメリット |
  |---|---|---|
  | **sqflite（採用）** | シンプル・依存パッケージが少ない・build_runner不要 | 生SQLを書く必要があり、スキーマが複雑化すると保守性が下がる |
  | drift | 型安全なクエリ、マイグレーション支援が強力 | build_runnerが必須。今回のような単一テーブル規模ではオーバースペック |
  | Hive / Isar（NoSQL系ローカルストレージ） | セットアップが手軽、キーバリュー的な保存に強い | 履歴の並び替え・件数上限管理等のクエリ操作はSQLの方が素直に書ける場面が多い |

  → 単一テーブルの検索履歴管理という規模感から、**sqfliteを推奨**。将来スキーマが複雑化した場合はdriftへの移行を検討する。

## 3. バックエンド構成

- **選定: 自前バックエンドは持たない（完全クライアント完結構成）**
- **理由**:
  - 検索履歴はローカル保存のみでクラウド同期しないため、永続化のための自前サーバーが不要。
  - 認証機能をMVPから除外したため、OAuthのコールバック処理・トークン検証・秘密鍵管理も不要。
  - 乗換案内API（Google Maps Platform）は外部SaaSにHTTPSで直接アクセスすれば足りる（後述の通り、APIキー漏洩リスクが許容できる形の運用にする）。
  - 個人開発・無料運用という制約に対して、最も学習コストと運用コストが低い構成。
- **比較した代替案とトレードオフ**:
  | 選択肢 | メリット | デメリット |
  |---|---|---|
  | **完全クライアント完結（採用）** | サーバー運用・言語学習が不要／無料枠で完結しやすい | 秘密情報の一部をクライアントに埋め込まざるを得ない（8章で緩和策を提示） |
  | 軽量BFF（Cloudflare Workers / Firebase Cloud Functions）を自作し、Google Maps PlatformのAPIキーをサーバー側に隠す | APIキーの秘匿性が最大化できる | サーバーサイド言語（TypeScript/Node等）の学習・実装・デプロイ管理が追加で必要。個人・未経験者には負荷が高い |
  | フル独自バックエンド（Node/Go等 + DB） | 自由度は最大 | オーバースペック。今回のスコープ（履歴は端末内、認証なし）には不要 |

  → 将来、乗換案内APIのキーを厳格に隠したくなった場合や認証機能を追加したくなった場合の**エスカレーションパス**として「軽量BFF」「Firebase Authentication」を選択肢として残すが、MVPでは採用しない（9章の未決定事項として明記）。

## 4. データベース設計方針

- **選定: 端末内ローカルDB（sqflite / SQLite）のみ。クラウドDBは使用しない。**（2.3参照）
- **理由**: 要件上、検索履歴はクラウド同期不可・ローカル保存のみと明記されているため、サーバーサイドDBは不要。
- **主要エンティティ（概要）**:
  - `SearchHistoryEntity`
    - `id` (PK, autoincrement)
    - `destinationStationName`（検索した目的駅名）
    - `destinationStationPlaceId`（Google Maps Platform側のPlace ID等、可能なら保持し再検索を高速化）
    - `searchedAt`（検索日時、履歴の並び替え・古い履歴の削除に使用）
    - `lastRouteSummaryJson`（直近の検索結果の要約を軽量にキャッシュ。オフライン時の明示表示に利用）
  - `CachedRouteEntity`（オフライン時にも直近の検索結果を表示するためのキャッシュ、`SearchHistoryEntity`と1:1でも可。将来的に分離を検討）
- **方針**:
  - 履歴の保存件数上限（例: 直近50件）を設け、無制限増加を防ぐ。

## 5. 認証・認可

- **MVPでは認証機能を持たない（確定）**。
- **理由**:
  - 検索履歴はクラウド同期しないローカル保存のみであり、ユーザーごとに出し分ける状態が現状存在しない。
  - 「調べる→確認するを最速に」というコンセプト上、起動直後にログイン画面を挟むことがユーザー体験上のマイナスになる。
  - Firebase AuthenticationやIdentity Platform（LINE OIDC統合）の導入・各社OAuthアプリ登録（審査待ちを含む）といった実装・運用コストを、MVPのスコープに対して避けられる。
- **将来の再検討条件**: 複数端末間での検索履歴同期など、ユーザー単位の状態を持つ必要が生じた場合に、Firebase Authentication（Google/Facebook/LINE優先、Xは後回し）の導入を再検討する。導入する場合の設計方針は本ドキュメントの旧版（Git履歴）を参照。

## 6. 外部連携

### 6.1 乗換案内API（経路検索）— 確定

要件定義書にて **Google Maps Platform（Routes API等）の採用が確定**した。他候補（駅すぱあとAPI、NAVITIME API、ジョルダン乗換案内オープンAPI、Yahoo!路線情報API）は要件定義書記載の理由により不採用が確定している。

- **採用: Google Maps Platform Routes API（`computeRoutes`、transitモード）**
  - 構造化JSONで経路・所要時間・乗換駅・徒歩区間を取得でき、独自UI（デザインシステムのカードUI）を組み立てやすい。
  - Google Cloudプロジェクトでのクレジットカード登録・毎月の無料クレジット枠内での運用にユーザーは同意済み。
  - Flutterからは `http` または `dio` パッケージで直接REST APIを呼び出す構成とする（専用の公式Flutter SDKは無いため、RESTクライアントとして実装）。
- **費用管理（確定）**: 無料クレジット枠内での運用を想定。Google Cloud Consoleの**予算アラート**を、**課金額が$1に到達した時点で通知が来るように設定**する方針を確定した。
  - **設定手順（概要）**:
    1. Google Cloud Console →「お支払い」→「予算とアラート」を開く。
    2. 対象のGoogle Cloudプロジェクト（トビノリ用）を選択し、新しい予算を作成する。
    3. 予算額を任意の金額（無料クレジット枠を踏まえた金額）で設定しつつ、**アラートのしきい値を「$1」に追加**する（金額指定でのしきい値、または予算額に対するパーセンテージ換算で$1相当になるよう設定）。
    4. 通知先メールアドレス（開発者本人のGoogleアカウント）にアラートが届くことを確認する。
  - これにより、無料クレジット枠を超えて実費課金が発生し始めた初期段階でいち早く気づける運用とする。

### 6.2 位置情報

- `geolocator` パッケージ(Android/iOS双方に対応するFlutter公式寄りのデファクトプラグイン)を利用し、現在地の取得・権限リクエストを行う。
- Android: `ACCESS_FINE_LOCATION` 権限、iOS: `NSLocationWhenInUseUsageDescription` の設定が将来のiOS対応時に必要。

### 6.3 最寄り駅までの経路案内（F-03）— 確定

要件定義書にて、**Googleマップアプリへのインテント連携によって徒歩ナビゲーションを委譲する方式**に確定した。アプリ内に独自の地図・道順UIは作り込まない。

- **実装方針**:
  - Android: `android_intent_plus` パッケージ、または `url_launcher` パッケージで `google.navigation:q=<緯度>,<経度>&mode=w` 形式のURIを起動し、Googleマップアプリの徒歩ナビゲーションへ遷移する。
  - iOS（将来対応）: `url_launcher` で `comgooglemaps://` カスタムURLスキーム、またはGoogleマップ未インストール時のフォールバックとして `https://maps.google.com/...` のWebフォールバックURLを使用する。
  - Googleマップアプリが端末に存在しない場合のフォールバック（ブラウザでのGoogleマップ表示等）を`url_launcher`の`canLaunchUrl`で判定した上で実装する。
- **要確認事項**: 開発者の端末にGoogleマップアプリがインストールされている前提で問題ないか（個人端末前提なので基本問題ないと想定）。

## 7. インフラ・ホスティング / CI・CD

- **配布形態**: Google Playストア・App Store審査は行わず、個人利用のみを想定。
  - Android: `flutter build apk` でビルドしたAPKを開発者本人のAndroid端末に直接インストールする（審査不要な野良アプリ的配布）。
  - iOS（将来対応時）: ストア配布を行わない場合でも、Appleの仕組み上、実機への長期インストールには基本的にApple Developer Programへの登録（年会費$99）が事実上必須であることは確定情報とする。ただし**費用負担そのものへの同意はiOS対応着手時までに判断する保留事項**とし、本ドキュメントでは確定させない（9章に記載）。TestFlightや個人開発者向けの配布方法は着手時に改めて確認する。
- **ホスティング**:
  - アプリ本体はホスティング不要（クライアント完結）。
  - 認証をMVPで持たないため、Firebase等のマネージドサービスへの依存もない。
- **CI/CD**:
  - 個人開発でストア審査もないため、大規模なCI/CDパイプラインは過剰。
  - 最低限、**GitHub Actions**で以下を自動化し、Claude Codeでの変更が壊れていないかを都度確認できるようにする。
    - `flutter analyze`（静的解析・Lint）
    - `flutter test`（ユニットテスト）
    - `flutter build apk --debug`（Androidデバッグビルドの疎通確認）
  - GitHub Actionsの `subosito/flutter-action` 等の公式寄りActionでFlutter SDKをセットアップし、YAML1本で完結させる。
  - 将来iOSビルドを追加する場合、GitHub ActionsのmacOSランナー（`runs-on: macos-latest`）上で `flutter build ios` を実行する構成に拡張する（Apple Developer Programの証明書・プロビジョニングプロファイル管理が別途必要になる）。
  - 署名済みリリースAPKの作成は手元の開発環境から `flutter build apk --release` で行うか、GitHub Actionsのsecretsに署名鍵（keystore）を登録して自動化するかは運用の手間次第（MVP段階ではローカルビルドで十分）。
- **テスト戦略**:
  - ユニットテスト（`flutter_test`）: 経路検索結果の整形ロジック、オンライン・オフライン判定ロジックなど、UIに依存しないドメイン層を重点的にテスト。

## 8. 非機能要件への対応方針

### 8.1 パフォーマンス（調べる→確認するを最速に）
- 起動直後にGPS取得と（可能なら）直近履歴の表示を並行して開始し、体感待ち時間を減らす。
- Google Maps Platform Routes APIへのリクエストにはタイムアウトを短く設定（例: 3〜5秒）し、応答がない場合は即座に8.2のオフライン表示へ切り替える。
- UIはデザインシステム通りsingle-column/single-purposeを徹底し、遷移回数を最小化する。

### 8.2 オフライン対応 — 確定方針

要件定義書にて、**電波が悪くオフライン状態（または劣化状態）になった場合は、裏側で自動的にフォールバックして見た目を変えないのではなく、「オフライン中です」等の表示でユーザーに明示的に状態を伝える方式**に確定した。以下の状態モデルを推奨する。

| 状態 | 判定方法 | 提供する機能・表示 |
|---|---|---|
| **オンライン（通常）** | ネットワーク接続あり＆Routes API応答あり | F-01〜F-04すべて通常提供 |
| **オフライン／劣化（電波弱・タイムアウト・接続なし）** | `connectivity_plus`パッケージで接続状態を監視、かつAPI呼び出しがタイムアウト・エラーとなった場合 | 画面上部などに**「オフライン中です」等の明示的なバナー・表示**を出し、新規の経路検索は行わない。ローカルDBに保存済みの検索履歴一覧とキャッシュ済みルート概要（`lastRouteSummaryJson`）の閲覧のみ提供する |

- 実装方針: `connectivity_plus`の接続状態監視と、Routes APIの短いタイムアウト設定を組み合わせ、Riverpodの状態（例: `connectivityStatusProvider`）としてオンライン/オフラインを一元管理し、UI側で明示的なバナー表示に反映する。
- GPSが取得できる場合、F-03（Googleマップアプリへの導線）はオフライン中でも起動を試行してよい（実際の徒歩ナビゲーションの可否はGoogleマップアプリ側のオフライン対応に委ねる）。

### 8.3 セキュリティ・秘密情報管理（Flutter/Dart環境向けに更新）

| 秘密情報の種類 | 管理方針（Flutter/Dart環境） |
|---|---|
| 経路検索API（Google Maps PlatformのAPIキー） | Google Cloud Consoleで**アプリケーション制限**（Android: パッケージ名＋SHA-1証明書フィンガープリント、iOS: Bundle ID）と**API制限**（Routes APIのみに限定）を必ず設定した上で、ビルド時に `--dart-define=MAPS_API_KEY=xxxx` （またはCI環境では `--dart-define-from-file` でJSONファイルから読み込み）でDartコードへ注入し、Gitにはコミットしない |
| ローカル開発時の秘密情報一式 | `flutter_dotenv` パッケージ、または単純に `--dart-define-from-file=env.json` のいずれかを利用。**推奨は `--dart-define-from-file`**（Flutter公式が案内する方式で、ネイティブのビルド設定に依存せずDart側だけで完結し、学習コストが低い）。`env.json`（実際の値）は`.gitignore`に追加し、`env.json.example`（キーのみ・ダミー値）をリポジトリに残してテンプレート化する |

- **Kotlinネイティブ時代（`local.properties` + `BuildConfig`）からの変更点**: Flutterでは同等の役割を `--dart-define` 系の仕組みが担う。Gradleの`BuildConfig`のようにネイティブビルド設定に依存しない分、Android/iOS両対応時も同じ手順で秘密情報を注入できる点がFlutter化のメリットの一つ。
- CI（GitHub Actions）でビルドする場合は、GitHub Secretsに`env.json`の中身（または個別キー）を登録し、ビルドジョブ内でファイルを生成してから`--dart-define-from-file`を使う運用とする。

### 8.4 スケーラビリティ
- 個人利用・単一ユーザー想定のため、スケーラビリティは設計上の主要関心事ではない。将来的に複数ユーザー・ストア配布を検討する場合は、3章で触れた「軽量BFF」導入や認証基盤の追加を再検討する。

### 8.5 アクセシビリティ・多言語対応
- 要件定義書側で「特に要件なし・今後検討」とされているため、本アーキテクチャでもMVP対象外とする。ただしFlutterの標準ウィジェットを使う限り、最低限のスクリーンリーダー対応（`Semantics`ウィジェット・`semanticLabel`付与等）は追加コストがほぼゼロなので、実装時に基本的な配慮は入れておくことを推奨する。

### 8.6 プライバシーポリシー
- 認証機能をMVPから除外したため、当面プライバシーポリシーの用意は不要と判断する。将来OAuthログイン等を導入し個人情報を取得・利用する段階になった時点で、簡易な静的ページ（GitHub Pages等）を用意する方針とする。
